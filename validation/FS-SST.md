| ID | Function | Implements | Design |
|---|---|---|---|
| FS-001 | `sst.regimes.load_regime()` reads `config/app.yaml` → `active_regime` and `config/regimes/<code>.yaml` into an immutable `Regime` object; `Regime.requires_audit(action)` / `requires_reason(action)` are the only decision points for record controls. | URS-001 | `sst/regimes.py` |
| FS-002 | `sst.audit.record()` inserts one `audit_trail` row (ts, actor, entity, entity_id, action, field, old_value, new_value, reason) for each mutation; timestamps via `utcnow()` (UTC, ms, `Z`). All write paths in `sst/main.py` call it inside the same transaction: create (`action=create`), delete (`action=delete`, field `status`), amendment (FS-009: `action=update`, one row per changed field among `measured_value`, `reportable_value`, `oos`, `status`, each with old and new value) and amendment verification (FS-010: `action=update`, field `status`). Amendment and verification rows are written through `_audit_updates()` before the `UPDATE assay_results` and committed with it. | URS-002, URS-009, URS-010, URS-011 | `sst/audit.py`, `sst/main.py::_audit_updates` |
| FS-003 | `record()` raises `ReasonRequired` when `requires_reason(action)` and `len(reason.strip()) < reason_min_length` (GMP: `update`, `delete`; 10 characters); `DELETE /api/results/{id}`, `_amend()` (FS-009) and `_verify()` (FS-010) map it to HTTP 422 and roll back, so the result row and the audit trail are unchanged. `DELETE /api/results/{id}` sets `deleted=1, status='Deleted'`; deleted rows are excluded from lists and from the JSON API (404), and amend/verify on a deleted result return 404. | URS-003 | `sst/audit.py`, `sst/main.py::api_delete_result`, `::_amend`, `::_verify` |
| FS-004 | `sst.rounding.evaluate(measured, lower, upper, mode)` → `(reportable, oos)`. `decimal_places()` derives precision from the limit text; `reportable_value()` uses `Decimal(str(x)).quantize()` with `ROUND_HALF_UP` (or `ROUND_HALF_EVEN` for regimes that configure it); `is_oos()` compares inclusively. Stored columns: `measured_value`, `reportable_value`, `oos`. | URS-004 | `sst/rounding.py` |
| FS-005 | HTML views `/`, `/samples`, `/samples/{id}` (Jinja2 templates) with per-row OOS highlighting and result counts. | URS-005 | `sst/main.py`, `sst/templates/` |
| FS-006 | `/results/{id}` (also for soft-deleted results) shows the result, its status and its `audit_trail` rows (record history, including the original value of an amended field as `old_value`); `/audit` lists the latest N entries; `/api/results/{id}/audit` returns them as JSON. No update or delete route exists for `audit_trail`. The result page shows: an amend form (measured value, pattern `-?\d+(\.\d+)?`; reason for change, `minlength` = `reason_min_length`) posting to `/results/{id}/amend`, only when the result is not deleted and not pending; when status is `Amended - pending verification`, a "Pending verification" banner (SOP-DI-004 §5.3) and a verify form (reason for verification) posting to `/results/{id}/verify` instead of the amend form; and any amend/verify error message as an alert. | URS-006, URS-010, URS-011 | `sst/main.py::_result_page`, `sst/templates/result.html` |
| FS-007 | `current_user()` reads `X-User` set by the SSO proxy (fallback `SST_USER` for local dev); it is stored as `analyst` on results and `actor` on audit rows. | URS-007 | `sst/main.py` |
| FS-008 | `POST /api/results` (201) validates `measured_value` as a decimal string, computes FS-004, writes the result and the `create` audit row; `GET /api/results/{id}`; `PATCH /api/results/{id}` (FS-009) with body `{measured_value, reason}`, `measured_value` validated by the `AmendIn` pattern `^-?\d+(\.\d+)?$` (422 otherwise); `POST /api/results/{id}/verify` (FS-010) with body `{reason}`; `DELETE /api/results/{id}` (FS-003). The amend form path validates `measured_value` server-side with the same pattern (`DECIMAL_RE`) after trimming, so values such as `1e3` or `abc` are rejected with 422. | URS-008, URS-010, URS-011 | `sst/main.py` |
| FS-009 | `_amend(conn, regime, actor, result_id, measured_value, reason)`, called by `PATCH /api/results/{id}` and form `POST /results/{id}/amend` (fields `measured_value`, `reason`), with `actor = current_user()`. In order: actor must be an active row in `users` (`provisioned_user()`, else 403) with a role in `AMEND_ROLES` = {QC Analyst, Senior QC Analyst, QC Supervisor} (403); trimmed `measured_value` must match `^-?\d+(\.\d+)?$` (422); result must exist and not be deleted (404); status `Amended - pending verification` → 409; `measured_value` text identical to the stored text → 422. Reportable value and OOS are recomputed with FS-004 `evaluate(measured, lower_limit, upper_limit, regime.results.rounding, regime.results.limit_inclusive)`. If the OOS flag changes and `regime.records.second_person_verification_on_oos_change` is true, status becomes `Amended - pending verification`, otherwise `Amended`. One FS-002 `update` audit row per changed field (`measured_value`, `reportable_value`, `oos`, `status`) with old/new value and the reason, then `UPDATE assay_results`, then commit; `ReasonRequired` → 422 and rollback (FS-003). API returns the updated result; the form redirects (303) to `/results/{id}` on success, and on 403/409/422 re-renders the result page with the error message and that HTTP status (404 is raised). | URS-010, URS-011, URS-002, URS-003, URS-004, URS-007 | `sst/main.py::_amend`, `::api_amend_result`, `::amend_result_form` |
| FS-010 | `_verify(conn, regime, actor, result_id, reason)`, called by `POST /api/results/{id}/verify` (body `{reason}`) and form `POST /results/{id}/verify` (field `reason`), with `actor = current_user()`. Actor must be provisioned (403) with a role in `VERIFY_ROLES` = {QC Supervisor} (403); result must exist and not be deleted (404); status must be `Amended - pending verification` (409); the actor must differ from the actor of the latest audit row that set `status` to `Amended - pending verification` (`_amended_by()`, else 403). Writes one FS-002 `update` audit row, field `status`, `Amended - pending verification` → `Amended`, with the reason, sets `status='Amended'` and commits; `ReasonRequired` → 422 and rollback. Form success/error handling as FS-009. Electronic signature for `amendment_verification` (`gmp.yaml` `e_signature.required_for`) is not implemented by this function. | URS-011, URS-002, URS-003, URS-007 | `sst/main.py::_verify`, `::_amended_by`, `::api_verify_amendment`, `::verify_amendment_form` |

Data model: `studies`, `batches`, `storage_conditions`, `specifications` (limits stored as text to preserve precision), `samples`, `assay_results`, `audit_trail`, `users` — see `sst/db.py` (schema version 7; unchanged by CHG-4127 — `assay_results.status` is free text and gains the values `Amended` and `Amended - pending verification`).

Change history: r3.4 (2025-05) approved baseline; r3.5-draft (CHG-4127, draft, not approved) FS-009 and FS-010 added for result amendment and second-person verification, FS-002/003/006/008 revised for the new write paths, page forms and API routes — see `deltas/URS-FS-delta-CHG-4127.md`.
